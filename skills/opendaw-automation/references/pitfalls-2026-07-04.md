# Pitfalls — openDAW MCP

## Werkstatt Processor API contract (CRITICAL — caused full rewrite of 7 scripts)

The real Werkstatt processor calls `proc.process(io, block)` where:
- `io` = `{src: [Float32Array, Float32Array], out: [Float32Array, Float32Array]}` — src=input channels, out=output channels
- `block` = `{s0, s1, p0, p1, bpm, flags, index}` — s0/s1 are sample range indices to process
- Parameters come through `paramChanged(label, value)` callback, NOT through a `parameters` array in `process()`
- `sampleRate` is on `globalThis` in the worklet, accessible in constructor and class field initializers

**WRONG (will compile but produce silence/errors at runtime):**
```javascript
class Processor {
  processAudio(inputs, outputs, parameters) {
    const gain = parameters.gain[0];  // parameters doesn't exist
    for (let c = 0; c < outputs[0].length; c++) { ... }  // wrong structure
  }
}
```

**CORRECT:**
```javascript
class Processor {
  constructor() {
    this.sr = sampleRate  // globalThis.sampleRate in worklet
    this.buf = new Float32Array(this.sr * 2)
    this.p = {drive: 0.3, mix: 0.8}  // param defaults
  }
  paramChanged(label, value) {
    this.p[label] = value  // store for use in process()
  }
  process(io, block) {
    for (let i = block.s0; i < block.s1; i++) {
      io.out[0][i] = io.src[0][i] * this.p.drive
      io.out[1][i] = io.src[1][i] * this.p.drive
    }
  }
}
```

Source: `WerkstattDeviceProcessor.ts` — `proc.process(this.#io, block)` at line 190. `UserProcessor` interface at line 39: `process(io: UserIO, block: Block): void` + optional `paramChanged(label, value)`.

## Apparat API (instrument — CONFIRMED)

Apparat generates audio from MIDI. Source: `ApparatDeviceProcessor.ts` line 186: `proc.process([outL, outR], block)`.

```javascript
class Processor {
  constructor() { /* sampleRate on globalThis, init oscillators/buffers */ }
  process(output, block) {
    // output = [Float32Array, Float32Array] — output channels (NO input)
    // block.s0, block.s1 — sample range
    // Instrument generates audio — no io.src, just write to output
    for (let i = block.s0; i < block.s1; i++) {
      output[0][i] = /* generate sample */
      output[1][i] = /* generate sample */
    }
  }
  paramChanged(label, value) { /* same as Werkstatt */ }
}
```

Key difference from Werkstatt: `process(output, block)` NOT `process(io, block)`. No input channels — instrument generates sound. Output is a 2-element array `[outL, outR]`, NOT an `{src, out}` object.

## Spielwerk API (MIDI effect — CONFIRMED)

Spielwerk transforms MIDI events. Source: `SpielwerkDeviceProcessor.ts` line 67: `process(block: UserBlock, events: Iterable<UserEvent>): IterableIterator<UserOutput>`.

```javascript
class Processor {
  *process(block, events) {  // MUST be a generator function (*process)
    // block = {from, to, bpm, s0, s1, flags} — from/to are ppqn positions
    // events = Iterable of {gate, pitch, velocity, position, duration, id, cent}
    for (const ev of events) {
      if (ev.gate) {
        yield { position: ev.position, duration: ev.duration, pitch: ev.pitch, velocity: ev.velocity }
      }
    }
  }
  paramChanged(label, value) {}
  reset() {}  // optional — called on transport stop
}
```

**CRITICAL:** `process` MUST be a generator (`*process`) that `yield`s note events. Returning an array does NOT work — the host iterates the return value as `IterableIterator`. If you return an array, notes are never played.

### Spielwerk ASI pitfall (generator after class fields)

When a generator method (`*process`) follows class field declarations, JavaScript ASI can misparse:
```javascript
class Processor {
  detune = 3          // ← no semicolon
  *process(block, e) { ... }  // ← parsed as: detune = 3 * process(block, e) { ... }
}
```
**Fix:** Add semicolon after the last class field before a generator method:
```javascript
  detune = 3;
  *process(block, e) { ... }
```
This only bites when `*process` directly follows a field. If there's a regular method (like `paramChanged`) between fields and `*process`, ASI handles it correctly. Verified: Node 20 `new Function()` validation catches this — `ScriptCompiler.validateCode` uses `new Function(wrappedCode)`.

## Maximizer at effect index 0 (CRITICAL — bites every session)

Upstream openDAW auto-adds a **Maximizer** to the Output unit's effect chain at **index 0**. When you add a Werkstatt or any effect via `add_effect`, it lands at index 1+, NOT index 0. If you pass `device_index=0` to scriptable device tools (`set_script_device_code`, `list_script_params`, etc.), you'll hit the Maximizer — which has no `.code`, `.parameters`, or `.samples` fields → "Cannot read properties of undefined" crash.

**Fix:** Before calling scriptable device tools, enumerate effects:
```javascript
const fx = h.effectBoxes(au);
const werkstattIdx = fx.findIndex(b => b.constructor.name === 'WerkstattDeviceBox');
```
Find by class name, not by hardcoded index.

## Script param mapping (v1.11.1+)

`@param` declarations support **4 mapping types**: `linear`, `exp`, `int`, `bool`. There is NO `unipolar` type in ScriptCompiler — if you omit the type or write `unipolar`, the param gets default mapping (0–1 range) but the `@param` line format is `// @param <name> <default> <min> <max> <type> [unit]`.

**CRITICAL:** The default value is MANDATORY. `// @param drive linear` fails — must be `// @param drive 0.5 0 1 linear`.
- `list_script_params` returns full mapping metadata (min/max/type/unit) parsed via `ScriptDeclaration.parseParams()` from the code string
- `set_script_param` validates and clamps values:
  - bool: snaps to 0 or 1 (value >= 0.5 → 1, else 0)
  - int: rounds to nearest integer, clamps to [min, max]
  - linear/exp/unipolar: clamps to [min, max]
- Returns `clamped` flag and `range` info in the response

### @param format
```
// @param <name>                    → unipolar 0–1, default 0
// @param gain 0.5                  → unipolar 0–1, default 0.5
// @param bypass false              → bool, default 0
// @param cutoff 1000 20 20000 exp Hz → exponential 20–20000, default 1000, unit Hz
// @param mode 2 0 4 int            → integer 0–4, default 2
// @param time 500 1 2000 linear ms → linear 1–2000, default 500, unit ms
```

### DAW_ScriptDeclaration global
`ScriptDeclaration.parseParams(code)` is available via `window.DAW_ScriptDeclaration` in headless-daw globals. Added in main.ts alongside `DAW_ScriptCompiler`. The code string is the single source of truth for mapping info — metadata is not stored in the box.

## Bridge evaluate returns dict, not string

`bridge.evaluate()` returns a Python dict/list/None directly from Playwright's `page.evaluate()`. MCP tools wrap it with `_wrap_eval(result)` → `json.dumps(result)` → string. When testing tools directly (not via MCP), use `json.loads(result)` to parse, or call `bridge.evaluate()` and handle the dict directly.

## Vite IPv6 vs IPv4 (localhost mismatch)

Vite binds to `[::1]:5174` (IPv6) by default. `curl localhost` resolves to `127.0.0.1` (IPv4) → connection refused, even though Vite is running fine. Puppeteer/Playwright resolves `localhost` correctly (tries IPv6 first). For direct curl tests, use `curl http://[::1]:5174/` or `curl http://127.0.0.1:5174/` explicitly. The bridge (`HeadlessDawBridge`) works regardless — Playwright handles the resolution.

To check: `ss -tlnp | grep 5174` shows `[::]:5174` or `127.0.0.1:5174` depending on config.

## JS syntax validation via bridge.evaluate()

`bridge.evaluate(script)` wraps the script in `async () => { return await (script)(); }` — so passing raw JS code (like a script file content) fails because it's not a function expression. To validate JS syntax of DSP scripts via the bridge:

```python
import json
code_escaped = json.dumps(code)  # safely embed JS code as string
# Pass a function expression that evaluate() can call
script = f'() => {{ try {{ eval({code_escaped}); return {{ ok: true }}; }} catch(e) {{ return {{ ok: false, error: e.message }}; }} }}'
result = await bridge.evaluate(script)
```

Key: `json.dumps()` for safe embedding (handles quotes, newlines, unicode). The outer `() => {...}` is the function that `evaluate()` calls. Inside, `eval()` parses the script as JS. `new Function(code)` does NOT work — it tries to execute the code body, not just parse it.

## Vite zombie port cascade (terminal killer)

When launching Vite via `node node_modules/vite/bin/vite.js --port 5174`, if port 5174 is occupied Vite auto-increments (5175, 5176, ...). Multiple background Vite starts create cascading zombie processes on ports 5174–5180+. Attempting `kill`/`fuser -k`/`pkill -f vite` from a foreground terminal can **hang the terminal indefinitely** (exit code 130, SIGINT).

**Prevention:** Always `pkill -f "vite"` and verify port is free BEFORE starting Vite. Use `ss -tlnp | grep 517` to check. If terminal hangs on kill commands, start a background process for the kill instead of foreground.

**Recovery:** If terminal is hung, start a background process (`background=true`) with `pkill -9 -f vite; sleep 1; echo cleared` and poll it. Foreground kill commands may not return.

## Bridge testing pattern for new DSP scripts

When testing a new Werkstatt/Apparat/Spielwerk script via the bridge, the correct API calls are:

1. **Create audio track** — `h.modify(() => { h.api.createAudioTrack(h.primaryAudioUnitBox); })` — MUST be inside modify()
2. **Add effect** — use `h.allAUBoxes()[idx]` (box, NOT adapter) → `h.modify(() => { h.api.insertEffect(auBox.audioEffects, factory); })` where `factory = window.DAW_EffectFactories.AudioNamed['Werkstatt']`
3. **Find device** — `const fx = h.effectBoxes(auBox); const werkstattBox = fx.find(b => b.constructor.name === 'WerkstattDeviceBox');`
4. **Compile script** — `const compiler = window.DAW_ScriptCompiler.create({headerTag:'werkstatt', registryName:'werkstattProcessors', functionName:'werkstatt'}); await compiler.compile(window.DAW_audioContext, h.editing, werkstattBox, codeString);`
5. **Read params** — `[...werkstattBox.parameters.pointerHub.filter()].map(p => ({label: p.box.label.getValue(), value: p.box.value.getValue()}))`
6. **Set param** — `h.modify(() => { param.box.value.setValue(newValue); })` — MUST be inside modify()

PITFALLS:
- `h.au(0)` returns an ADAPTER, `h.allAUBoxes()[0]` returns a BOX. `insertEffect` expects `auBox.audioEffects` (field on box), not adapter field.
- `h.api.createEffect()` does NOT exist — use `window.DAW_EffectFactories.AudioNamed['Werkstatt']` directly as the factory argument to `insertEffect`.
- `new window.DAW_ScriptCompiler()` does NOT exist — use `window.DAW_ScriptCompiler.create(config)` static factory method.
- `device.parameters.pointerHub.filter()` is the correct iteration method (NOT `.incoming()`).
- `api.createTrack()` does NOT exist — use `api.createAudioTrack(auBox)` (inside modify block).

After killing zombie Vite processes, a fresh `node node_modules/vite/bin/vite.js --port 5174` may start but produce **zero output** and never listen on any port. The process runs (PID exists, `status=running`) but stdout/stderr are completely empty and `curl localhost:5174` returns 000. This is NOT the zombie cascade — ports are confirmed free via `ss -tlnp`, `http.createServer` works on 5174, `node -e` works, vite dist/ exists, vite.config.ts is valid.

**Likely cause:** WSL networking state degradation after multiple aggressive `pkill -9` cycles, or Vite's internal optimizer silently failing after node_modules were emptied by an upstream rebase (even though headless-daw has its own node_modules, shared deps may be stale). The `process` tool captures zero output because Vite's stdio buffering doesn't flush before the process is killed.

**Workaround:** If Vite won't start after 3 attempts with cleared ports:
1. Try `npx vite --port 5174` instead of `node node_modules/vite/bin/vite.js` (different module resolution)
2. Check if headless-daw node_modules need refresh: `ls node_modules/.bin/vite` — if missing, the install is broken
3. As a last resort, test DSP scripts via `node --check script.js` for syntax validation + `new Function(code)` for compile validation — these don't need Vite running
4. Do NOT loop more than 3 Vite start attempts — the bridge E2E tests auto-skip if DAW is not running, so unit tests (93) still pass without it
