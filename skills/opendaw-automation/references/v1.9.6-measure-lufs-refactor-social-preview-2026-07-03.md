## measure_lufs Refactoring

### Problem
`measure_lufs` was a 223-line monolith — WAV parsing + K-weighting + gated mean squares + true peak all inline. Untestable without a real WAV file on disk.

### Solution: Extract two pure-Python helpers

**`_parse_wav(raw: bytes) -> dict`** — RIFF/WAVE parser. Returns `{audio_format, n_channels, sample_rate, bits_per_sample, n_frames, channels}`. Supports float32 (format=3), PCM16/24/32 (format=1). Raises `ValueError` on invalid input.

**`_compute_lufs(channels: list, sample_rate: int) -> dict`** — ITU-R BS.1770-4. Returns `{lufs_integrated, true_peak_db, max_sample, blocks_measured, gated_blocks}`.

`measure_lufs` itself became 20 lines:
```python
with open(filepath, "rb") as f:
    raw = f.read()
wav = _parse_wav(raw)
lufs_data = _compute_lufs(wav["channels"], wav["sample_rate"])
return json.dumps({"success": True, **lufs_data, "duration_seconds": ..., "sample_rate": ..., "channels": ...})
```

### DRY fix: K-weighting coefficient duplication

The original code had `if sample_rate == 48000: ... else: ...` — both branches were **identical** (both used `sample_rate` in `math.tan()` formula, not hardcoded 48000 constants). Merged into single computation block. -29 lines.

### Test WAV generator struct field order (CRITICAL)

When generating test WAV files with `struct.pack("<HHIIHH", ...)`, the field order MUST match RIFF fmt chunk layout:

```
format(2) → channels(2) → sample_rate(4) → byte_rate(4) → block_align(2) → bits_per_sample(2)
```

**Bug found by tests**: `_make_wav_float32` originally packed `bytes_per * 8` (32) as the 5th field (block_align) and `0` as 6th (bits_per_sample). Parser then read `bits_per_sample=0` → `bytes_per_sample = 0 // 8 = 0` → `ZeroDivisionError`.

**Fix**: 5th field = `n_channels * bytes_per` (block_align), 6th field = `bytes_per * 8` (bits_per_sample).

## Social Preview Banner (GitHub OpenGraph)

### Why
0 views, 0 stars, 0 clones — repo was invisible. GitHub auto-generated OpenGraph image (just README text) is unappealing. Custom social preview improves click-through from links.

### Process
1. Write SVG (1280×640, dark theme, monospace, badges + features + architecture chain)
2. Convert to PNG: `pip install cairosvg && python3 -c "from cairosvg import svg2png; svg2png(url='input.svg', write_to='output.png', output_width=1280, output_height=640)"`
3. Commit to `assets/social-preview.png` in repo
4. GitHub repo settings → Social preview → upload (manual web UI step — no API for this)

**Note**: GitHub OpenGraph requires PNG/JPG, not SVG. `rsvg-convert`/`convert`/`inkscape` may not be available — `cairosvg` Python package is the reliable fallback.

### SVG template structure
- Dark gradient background (`#0a0a0f` → `#1a1a2e`)
- Title + subtitle in monospace
- Accent gradient line (purple → blue)
- Badge rectangles (tools count, tests count, CI status, license)
- Feature highlights with emoji
- Architecture chain at bottom
- Waveform decoration bars (low opacity)

## awesome-mcp PR Update via REST API (GraphQL Deprecation Workaround)

### Problem
`gh pr edit` failed with: `GraphQL: Projects (classic) is being deprecated in favor of the new Projects experience`. The CLI uses GraphQL for PR edits, which now errors on projects-related fields.

### Solution: Use REST API directly
```bash
gh api repos/<owner>/<repo>/pulls/<PR_number> \
  --method PATCH \
  -f title="New title" \
  -f body="New body" \
  --jq '.title'
```

This bypasses the GraphQL layer entirely. Works for title and body updates. Confirmed working on `punkpeye/awesome-mcp-servers` PR #9133.

### Lesson
When `gh pr edit` / `gh issue edit` fail with GraphQL deprecation errors, switch to `gh api ... --method PATCH` on the REST endpoint. The `gh` CLI's GraphQL path is increasingly unreliable for PR operations.
