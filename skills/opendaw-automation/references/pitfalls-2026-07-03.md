# Operating Pitfalls (accumulated)

## Python vs JS context confusion (F821 — CRITICAL)

`h` (DAW_HELPERS) is a JS-only object injected into the browser context via `page.evaluate()`. Using `h.ppqn.Quarter` or `h.anything` in **Python-side** code causes `NameError` at runtime.

```python
# WRONG — crashes with NameError:
new_ppqn = int(new_position_beats * h.ppqn.Quarter)

# CORRECT — PPQN.Quarter = 960, hardcoded in Python:
new_ppqn = int(new_position_beats * 960)
```

ruff F821 (undefined-name) catches these statically. **Always run ruff after editing tool bodies.** Unit tests can't catch this because the tools require `bridge.evaluate()` which needs a running DAW.

Affected tools found and fixed: `move_automation_event`, `get_automation_value`, `move_region_content`.

## DRY: duplicated if/else branches

Before writing `if sample_rate == 48000: ... else: ...`, verify the branches are actually different. If both branches use the `sample_rate` variable (not hardcoded 48000 constants), they're identical code — merge them.

This was the case for K-weighting biquad coefficients in `measure_lufs`: 29 lines of pure duplication.

## Test WAV generator struct field order

When generating test WAV files with `struct.pack("<HHIIHH", ...)`, the field order MUST match RIFF fmt chunk layout:

```
format(H) → channels(H) → sample_rate(I) → byte_rate(I) → block_align(H) → bits_per_sample(H)
```

**Bug found by tests**: `_make_wav_float32` originally packed `bytes_per * 8` (32) as the 5th field (block_align) and `0` as 6th (bits_per_sample). Parser then read `bits_per_sample=0` → `bytes_per_sample = 0 // 8 = 0` → `ZeroDivisionError`.

**Fix**: 5th field = `n_channels * bytes_per` (block_align), 6th field = `bytes_per * 8` (bits_per_sample).

## awesome-mcp PR maintenance (GraphQL deprecation)

`gh pr edit` fails with: `GraphQL: Projects (classic) is being deprecated`. The CLI uses GraphQL for PR edits, which now errors on projects-related fields.

**Solution**: Use REST API directly:
```bash
gh api repos/<owner>/<repo>/pulls/<PR_number> \
  --method PATCH \
  -f title="New title" \
  -f body="New body" \
  --jq '.title'
```

Keep PR title/body synced with current tool count and features after each release.

## Cross-repo PR creation limitations

`gh pr create --repo appcypher/awesome-mcp-servers --head AMEOBIUS:branch` may fail with: `GraphQL: AMEOBIUS does not have the correct permissions to execute CreatePullRequest`.

Branch push to fork succeeds. PR creation needs:
- Browser: open `https://github.com/<upstream>/<repo>/compare/main...AMEOBIUS:<branch>?expand=1`
- OR token with broader cross-repo scopes

## CairoSVG for PNG conversion

GitHub OpenGraph preview requires PNG/JPG (not SVG). System SVG converters (`rsvg-convert`, `convert`, `inkscape`) may not be available.

**Reliable fallback**: `pip install cairosvg && python3 -c "from cairosvg import svg2png; svg2png(url='in.svg', write_to='out.png', output_width=1280, output_height=640)"`

## Refactoring for testability pattern

When a tool function is too large to unit test:
1. Extract pure-Python logic (no bridge dependency) into standalone helpers
2. Helper takes primitive types (bytes, lists, ints) and returns dicts
3. Tool function becomes a thin wrapper: read file → call helper → format JSON
4. Write unit tests against the helper (generate synthetic input data)

Applied to `measure_lufs`: 223 lines → 20-line wrapper + `_parse_wav()` + `_compute_lufs()`. 9 new tests covering WAV parsing and LUFS computation without needing real audio files.

## ScriptCompiler migration (v1.9.7 — replaces custom @param regex parser)

`set_script_device_code` now uses the **official `ScriptCompiler`** from `@opendaw/studio-adapters` instead of hand-rolled regex parsing. This was prompted by discovering naomiaro/opendaw-test documentation showing the correct compile flow.

**What changed:**
- `DAW_ScriptCompiler` global added to `headless-daw/src/main.ts` (from `adapters.ScriptCompiler`)
- `set_script_device_code` creates a compiler via `ScriptCompiler.create(config)` where config = `{headerTag, registryName, functionName}` per device type
- Compiler configs match upstream exactly:
  - werkstatt: `{headerTag: "werkstatt", registryName: "werkstattProcessors", functionName: "werkstatt"}`
  - apparat: `{headerTag: "apparat", registryName: "apparatProcessors", functionName: "apparat"}`
  - spielwerk: `{headerTag: "spielwerk", registryName: "spielwerkProcessors", functionName: "spielwerk"}`
- `compiler.compile(ctx, editing, device, source)` handles EVERYTHING: parsing @param/@sample, creating WerkstattParameterBox/WerkstattSampleBox children, writing code header, validating JS, registering worklet. The tool just calls it and reads back results.

**Why this is better than the old custom parser:**
- ScriptCompiler caches declarations in a WeakMap — identical @param declarations don't trigger box recreation
- Proper sample file cleanup (deletes orphaned AudioFileBox when @sample removed)
- Label parsing from code (`// @werkstatt myEffect 1 1` → `device.label.setValue("myEffect")`)
- Uses the exact same code path as the upstream studio app — no drift
- `editing.modify()` is called INSIDE compile() (the SDK owns the transaction)

**Beware:** `add_effect(effect_type="werkstatt")` is case-sensitive — factory keys are Capitalized (`Werkstatt`, not `werkstatt`). The `ef.AudioNamed[effectType]` lookup fails on lowercase. Either pass `"Werkstatt"` or add case-insensitive lookup.

## Stem export useInstrumentOutput bug (v1.9.7 fix)

**BUG:** `export_stems` and `export_single_stem` had `useInstrumentOutput: True` while docstring claimed "effects included". This produced DRY stems (raw instrument output, no effects/channel strip).

**FIX:** Changed to `useInstrumentOutput: False` — stems now route through the channel strip (effects, sends, volume/pan all baked in). This matches naomiaro documentation: `"useInstrumentOutput": false` → effects, sends, and the strip's volume/pan reach the render.

**New tool `export_dry_stem`** added for the opposite case (freeze/flatten/re-amp): `useInstrumentOutput: True`, `includeAudioEffects: False`, `includeSends: False` captures the raw instrument signal.

**Rule of thumb:** `useInstrumentOutput=False` = wet (with effects), `True` = dry (instrument only). Most stem export use cases want `False`.
